# v0.5.7：周囲の配置・密度・階段・打鍵時刻

2026-09-28、v0.5.7で片手密度、同色階段、隣接階段、ホーム運指を崩す階段の負荷を追加。AGEHAの規則的な同色階段、R3の無理皿、MOON RACE HYPERの偏った16分配置に対するユーザーの指摘を受けた更新。曲名や既存評価による加点・減点は入れていない。以下は実プレイで未校正の仮説であり、LIGHTNING MODELの判定プログラムや人体の完全な再現ではない。

## 周囲をどこまで見るか

v0.4は運指選択で次の1動作、認識で直近2動作を主に参照していた。v0.5の配置認識は手ごとに、過去最大7動作（2秒以内）と未来最大7動作（標準0.65秒以内）を使う。運指候補の先読み自体は従来の次の1動作まで。譜面全体を知った最適運指探索ではない。

- **同色の流れ**：同じ色の異なる単鍵3個が、ほぼ一定の間隔で続くもの。各間隔は350ms以内、間隔差15%以内。隣接階段や白黒をまたぐ階段とは分ける。
- **規則的な反復**：3～6動作の単鍵フレーズが2回現れ、3種類以上の鍵盤を含み、等間隔の条件を満たすもの。認識範囲内で確認できたときに軽減する。
- **縦連**：同色でも同じ鍵盤の繰り返しには上記軽減を掛けない。ほかの鍵盤を挟んでも、そのレーンの前回時刻を保持して追加負荷を計算する。

同色習熟0.9、フレーズ習熟0.8を標準とする。これは学習済みプレイヤーの実測尺度ではない。同色の流れと反復の軽減は認識・動作を段取りする部分に掛け、移動距離、押下仕事、指の回復時間は消さない。

1秒窓の片手動作頻度と忙しい指の頻度を、負荷に直接反映する。片手が5動作/秒を超える分と最忙指が4動作/秒を超える分へ漸増負荷を加え、同じ片手の速い連続動作には別の小さな負荷を加える。全体密度は譜面の打鍵機会とゲージ消費にそのまま残す。パターンを覚えても、速く押し続ける身体負荷は消さない。

片手密度負荷は `0.2×max(0, 有効片手頻度−5) + 0.2×max(0, 最忙指頻度−4)`。同じ手で145ms未満の間隔が続くと1動作ずつ連続数を数え、4動作を超えた分に最大1.2の追加負荷を加える。同色の流れや規則反復が認識された場合、この連続動作負荷を最大60%軽減するが、片手密度自体は消さない。ここでの閾値・係数は未校正。

階段は同一レーン差が1～2の単鍵で、2回以上同じ方向へ進む列を認識する。飛び幅が一定でない列も対象にする。規則的な同色階段は、3動作が約同間隔で、毎回同じ色・同じ方向へ2鍵ずつ進むものとする。習熟による認識軽減はこのタイプだけに適用する。隣接鍵を含む階段（1鍵差）は別に識別し、規則性による軽減をせず、隣接階段の身体負荷を加える。

階段中の割り当て指がホーム運指 `1親23人4中56薬7小` から外れる場合、一般の拡張運指負荷に加え、ホーム配置を崩す階段の追加負荷を加える。その区間の階段認識軽減も外す。これは「規則的なら全て簡単」としないための区別。係数は仮置きで、プレイヤーによる実測・校正はまだない。

## 判定は入力時刻から計算する

v0.4では各ノーツの負荷からBAD・POORを直接抽選していた。v0.5は、負荷から取りこぼしや大きなタイミング乱れを発生させ、打鍵予定時刻に以下を加えて実際の入力列を作る。

1. 全体の早打ち・遅れ（標準0ms）
2. 打鍵ごとのばらつき（標準18ms、正規分布の近似）
3. 同レーンの連打・連皿に残るズレ（標準では次の入力で20%戻す）
4. 連打テンポの継続的な加速・減速（標準0）
5. 担当指の前の入力から、最低限の再打鍵時間を確保するための遅れ

鍵盤を離して再打鍵する待ち時間は、鍵盤の入力だけに適用する。連皿は同じ指を接触させたまま往復するので、この制約を流用しない。皿の力・切り返し負荷と、同レーンのタイミングずれは引き続き評価する。

入力を時刻順に処理し、ノーツが判定済みかをレーンごとに追跡する。入力1回で消えるノーツは最大1個。既に消えたノーツは再判定しない。入力を予定したノーツと実際に判定されたノーツが異なるケースを数える。時間切れで見逃しPOOR、近くに判定対象がない余分な入力は条件により空POORとなる。ゲージの減少も入力・時間切れが実際に起きた順で行う。

### 判定窓と優先順は仮定

| 項目 | 標準設定（片側幅） |
|---|---:|
| PGREAT | 16.67ms |
| GREAT | 33.33ms |
| GOODまで | 100ms |
| BADまで | 200ms |

この表は**本実験の設定値**であり、現行ACの実測値を示す表ではない。特にGOOD/BAD幅100/200msは仮定。画面から判定窓を変更できる。旧文書のゲージ資料から実機内部の判定順まで確定したとは扱わない。

優先順は「同レーンのGOOD以内で最も近い未処理ノーツ → BAD以内で最も古い未処理ノーツ」。この優先順、空POORの範囲、フレーム・入力走査単位、DP皿固有の判定幅はLM実機で未検証。GAMBOLなどの個別判定窓も未対応。

## BADハマりの扱い

早い入力が次のノーツをBADで消すと、その次の入力もさらに先のノーツへ判定され得る。加えて同レーンのリズムずれを持ち越すため、誤差が独立な抽選だけの場合と違い、連続BADが発生する。鍵盤と皿に同じレーン判定の仕組みを使う。

表示する「同レーンでBADが3回以上続く区間」は600ms以内に続いたBAD列の数。「BADハマり」を実プレイから観測した数ではなく、本モデル内での診断指標。立て直しはズレを徐々に戻す近似で、プレイヤーが意図的に一拍休む、音を聞いて修正する、視線を切り替えるといった戦略の探索は未実装。

早い・遅い入力数、平均時刻差、BAD連続数、予定外のノーツに付いた判定、1試行目の判定例を表示する。時刻差は**実際に判定されたノーツ**を基準とし、負が早打ち、正が遅れ。見逃し・空POORには対応する時刻差がない場合がある。

## あんみつ

標準の一覧評価では無効。個別再試行で「まとめる間隔」を設定すると、同じ手の隣り合う2動作を中間の時刻へ移す候補を使う。

- 異なる鍵盤で、ホーム運指上の指が重ならない組合せに限定する。
- 同レーンの連打、皿、CN/BSS端点、保持中の動作はまとめない。
- 設定した間隔、先読み時間、仮のGOOD窓から20msの余裕を引いた範囲をすべて満たす。
- 元譜面のノーツ数と判定時刻は保存し、動作側だけをまとめる。移動負荷はまとめた動作で計算し、判定は元の時刻に対して個別に行う。
- タイミングの乱れや他ノーツとの競合で失敗することもあり、常に有利とは限らない。曲全体の最適なあんみつ配置を探索する機能ではない。

## 同時皿の到達範囲とずらし

ユーザーの左手の運指説明を標準の境界に採用した。右手は左右反転の仮定であり、左右それぞれの実測ではない。

| 左手の鍵盤 | 右手に反転した鍵盤 | 同時皿の扱い |
|---|---|---|
| 1・2・3 | 7・6・5 | 鍵盤を親指／人差し指、皿を小指／薬指で分担 |
| 4 | 4 | 同じ指分担だが、限界付近として追加負荷1 |
| 5・6・7 | 3・2・1 | 通常の同時到達は不可、ずらしが必要 |

さらにmm距離が設定した手幅を超える配置も同時到達不可とする。手幅を大きくしても左5～7の境界は消えない。手の関節や指の曲げ方を解いた普遍的な人体限界ではなく、このプレイヤー像に対する明示的な制約である。通常のホーム限定設定でも、同時皿では専用の親／人運指を使う。

通常タップの無理皿では、最も遠い鍵盤から皿までの距離を既存の移動時間式 `35 + 45×log2(1 + 距離/有効押下面幅)` ms に入れ、鍵盤を先、皿を後に取る予定を作る。標準設定では移動時間を早打ち・遅打ちへ半分ずつ配分する。先読みが短い場合は鍵盤の前倒しをその範囲に抑え、残りを皿の遅れへ回す。元譜面の判定時刻は一切移さないため、移動できてもGOOD範囲を超えればBADとなる。

画面の「同時皿の遅打ち」を正の値にすると、届く同時皿も含めて皿の遅れを指定する。無理皿では移動時間の不足分だけ鍵盤を早める。0は「無理皿だけ自動ずらし」。単独の連皿、CN/BSS端点、ずらす区間に保持がある動作は対象外。保持のためにずらせない無理皿は皿を見逃す。BSS保持中の届かない鍵盤は鍵盤を見逃すという固定方針で、保持を捨てる戦略との最適比較は行わない。

これは局所的な予定であり、周囲の全ノーツとの衝突を避ける最適経路探索ではない。予定に加えた時刻のばらつきが実移動速度に与える制約、手首・側面での接触、押下面のどこを狙うかの最適化は未解決。標準の早打ちと遅打ちへの配分が実際のユーザーの取り方を再現するとまでは言えない。

## AGEHAとR3の解釈

AGEHA ANOTHERには、解析した難所で白鍵3個・黒鍵3個の流れとフレーズ反復が確認できた。旧版では片手の動作頻度の重みが大きく、複数指で規則的に流す利点を十分に扱っていなかった。新版はこの性質を曲名に依存せず検出する。

ユーザーの条件はAGEHAが正規、R3が何らかの固定配置。R3では鍵盤を先に取り、皿を急いで遅打ちしていた。新版は上記の到達境界とずらしを扱うが、R3の体感との不一致を解決したとはまだ言えない。一覧は固定配置と両RANDOMの候補を比較しているので、体感比較にはAGEHA正規とR3の固定配置の数値も併記する。R3で使った固定配置は特定されていないため、固定最良も実際の条件と同一とは限らない。R3をAGEHAより上へ強制する補正は入れていない。

`data/context-timing-validation.json` に2曲の変更前後の必要能力と特徴を記録する。能力の尺度自体も変わるため、数値差を実難度の差や精度改善率とは解釈しない。全件の再換算後の☆は別途一覧を参照する。
